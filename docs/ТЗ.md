# ТЗ: 2D изометрическая RPG с пошаговыми кубиковыми боями

## 1. Назначение документа

Зафиксировать технологический стек, архитектуру и состав систем игры до начала
разработки. Документ отвечает на вопрос «как строить», а не «про что игра».

**Вне рамок этого ТЗ (делается отдельно):** сюжет, тексты, персонажи, лор, баланс
чисел, ассеты. Под них в архитектуре зарезервированы места (раздел 7), контент
задаётся данными, а не кодом.

## 2. Концепция и референс

| Параметр | Значение |
|---|---|
| Жанр | RPG с пошаговыми боями |
| Перспектива | 2D изометрия (тайлы 2:1) |
| Боевая система | Пошаговая: бросок кубиков, распределение значений по слотам экипировки. Референс — *Dicey Dungeons* (Terry Cavanagh) |
| Платформы | Android, iOS, Windows/macOS/Linux. **Web не поддерживается** |
| Режим | Одиночный, офлайн |
| Движок | Flutter + Flame (обоснование — раздел 3) |

Геймплейный цикл: исследование изометрического мира/подземелий → столкновение →
пошаговый бой с кубиками → награды/прокачка → возвращение в мир.

## 3. Технологический стек и его обоснование

**Вывод: Flutter + Flame задачу решают, движок менять не нужно.**

Проверено на реальном API установленного `flame 1.35.1`:

- **Изометрия есть «из коробки»** — `IsometricTileMapComponent` (рендер тайлов,
  параметр `destTileSize` для масштаба блока), плюс `Shadow3dDecorator` для
  теней-псевдо-3D.
- **Маршрутизация сцен** — `RouterComponent` + `Route`/`WorldRoute`: навигация
  между экранами с управлением time-scale, прозрачностью, анимациями переходов.
- **Камера** — `CameraComponent` + `World` (следование за игроком, зум).
- **Карты** — `flame_tiled 3.1.2` доступен (подтянет flame до `1.38.2`; версию
  зафиксировать при старте разработки).
- **Анимации/частицы/текст/UI** — `SpriteAnimationComponent`, параллакс,
  `TextPaint`, `SpriteBatch` для батчинга спрайтов.
- **Стейт** — `riverpod` (или `flame_riverpod` для прокидывания в компоненты).

**Почему подходит именно этому жанру:** бой в Dicey Dungeons — пошаговый и
UI-тяжёлый (панель кубиков, слоты экипировки, эффекты статусов). Это не
realtime-экшен, поэтому нет жёстких требований к физике и стабильному fps в
боёвке; здесь Flutter раскрывается сильнее, чем в динамичных жанрах.

**Где у Flutter/Flame слабые места и что с ними делать:**

| Проблема | Решение |
|---|---|
| Нет встроенного pathfinding | Свой A* на сетке тайлов (это ~100 строк), или пакет |
| Сортировка глубины изометрии для высоких объектов | Ручная сортировка по Y-координате ноги спрайта |
| Изометрические коллизии | Слой коллизий в Tiled + проверка тайла под позицией |
| Производительность текста | Не создавать `TextPaint` в `render`; кэшировать |
| Web | Не таргет (заявлено осознанно) |

## 4. Архитектура

### 4.1. Слоёная структура

Главный принцип: **игровая логика отделена от отображения и знает про Flutter/Flame
только в крайнем случае.**

```
┌─────────────────────────────────────────────────────────────┐
│ Presentation — Flame компоненты и Flutter-оверлеи           │
│ (игровой мир, анимации, HUD, меню, боёвка)                  │
├─────────────────────────────────────────────────────────────┤
│ Game Logic — чистый Dart, тестируемый без виджетов          │
│ (бой, инвентарь, прокачка, статы, броски кубиков, AI врагов)│
├─────────────────────────────────────────────────────────────┤
│ Domain Data — immutable-модели контента                     │
│ (предметы, классы, враги, способности — из JSON)            │
├─────────────────────────────────────────────────────────────┤
│ Persistence — сейвы (JSON/Hive), настройки, прогресс        │
└─────────────────────────────────────────────────────────────┘
```

Слой `Game Logic` — ядро, который мы начинаем строить первым и покрываем
unit-тестами. Presentation подписывается на его состояние и перерисовывается.

### 4.2. Подход к экранам

Разделить на две независимые части:

1. **Игровой мир (Flame)** — `World` + `CameraComponent` + компоненты:
   плеер, нпс, враги на карте, тайлы изометрии. Через `RouterComponent`
   переключаются маршруты: главное меню → мир → бой → пауза/инвентарь.
   **Факт реализации (ревизия 1):** `RouterComponent` пока не нужен — экраны
   меню/боя/инвентаря сделаны Flutter-оверлеями (см. ниже), а смена локаций
   идёт перезагрузкой содержимого одного `World`. Маршруты добавим, когда
   появится главное меню как отдельная сцена.
2. **UI поверх игры** — HUD (здоровье, мана/кубики, инвентарь) и сама боёвка
   реализуются Flutter-оверлеями поверх `GameWidget`. Кидание кубиков и
   драг-н-дроп в слоты — это стандартный `Draggable`/`DragTarget` Flutter,
   к нему проще прикрутить доступность, жесты и тесты, чем к кастомным
   Flame-жестам. Бой должен ощущаться как настольная игра — этому соответствует
   нативный UI.

Связь: `GameWidget.overlayBuilderMap` + `game.overlays.add/remove`.

### 4.3. Стейт-менеджмент

- `riverpod`-провайдеры для всего, что живёт между экранами: текущий забег,
  партия/персонаж, инвентарь, настройки, прогресс меты.
  **Факт реализации (ревизия 1):** вместо riverpod пока используется
  `ChangeNotifier` (`GameState`, `BattleEngine`, `NotificationService`) —
  меньше зависимостей и хватает для одиночной офлайн-игры. Переход на
  riverpod оставлен на потом, когда провайдеров станет много.
- Внутри боя — отдельный стейт-объект боя (`BattleState`), который логика
  мутирует, а UI слушает (например, через `ValueNotifier` или state-провайдер).
  История ходов хранится для отката и анимаций.
- Flame-компоненты читают стейт только в `update`/`render`, не мутируют
  логику напрямую — действия проходят через команды.

### 4.4. Игровой цикл и сохранения

- Вне боя игра идёт в реальном времени (перемещение по карте), бой — пошаговый.
- Сейвы — сериализация состояния в JSON (или Hive для скорости на мобайлах):
  позиция на карте, инвентарь, уровни, флаги событий (для сюжетной системы,
  раздел 7). Автосейв на переходах между сценами.

## 5. Системы (состав)

| Система | Ответственность | Примечания |
|---|---|---|
| Изометрический рендер | Отрисовка карты, сортировка глубины, тени | `IsometricTileMapComponent` |
| Перемещение | Движение игрока по сетке, pathfinding A* | Управление: тап-ту-мув на мобайлах, WASD/стрелки на десктопе |
| Столкновения/зоны | События на тайлах, переходы между картами | Слой объектов в Tiled |
| Бой (ядро) | Очередь ходов, броски кубиков, слоты экипировки, статусы, AI врагов | Чистый Dart, тесты — раздел 5.1 |
| Бой (UI) | Кости, слоты, перетаскивание, анимации эффектов | Flutter-оверлей |
| Экипировка/инвентарь | Предметы, наборы кубиков от экипировки | Контент из JSON |
| Прокачка | Уровни, характеристики, классы | Контент из JSON |
| Диалоги/события | Вывод реплик, ветвления, флаги | Данные сюжета подключаются позже — раздел 7 |
| Звук | Музыка, SFX | `flame_audio` |
| Настройки/сейвы | Язык, громкость, управление, автосейв | — |

### 5.1. Боевая система — модель

Скелет модели боя (детали и баланс — позже):

- **Кубик** — граней N, значения на гранях; бросок = генерация случайного значения.
  В экипировку встроены правила приёма значений в слоты (например, «только
  чётное», «сумма двух костей»).
- **Слот экипировки** — принимает кубик по правилу; при помещении — эффект
  (урон / лечение / щит / наложение статуса).
- **Раунд** — у каждого бойца очередь хода; на ходе — бросок своего пула кубиков
  и распределение по слотам; слот можно не заполнять.
- **Статусы** — горение, отравление, оглушение, щит и т.д. — модификаторы
  в начале/конце хода.
- **Враги** — ИИ описан данными (приоритеты слотов, агрессия), без хардкода
  поведения под каждого врага.

## 7. Куда подключится сюжет

Сюжет пишется отдельно — под него зарезервированы два данных-управляемых входа,
чтобы тексты не потребовали изменений в коде:

1. **Диалоговая система** — реплики, ветвления, условия по флагам событий.
   Формат — JSON или Ink (https://www.inklestudios.com/ink/) при большей
   сложности. UI один, меняется только содержимое.
2. **Флаги событий** — булево/числовое хранилище прогресса в сейве; используются
   условиями диалогов и карт (открытие проходов, появление нпс).

Также контент (предметы, классы, враги, способности) вынесен в `assets/data`,
чтобы баланс и наполнение правились без пересборки кода.

## 8. Что не входит в ТЗ

- Сюжет, тексты, персонажи, лор — пишет автор.
- Численный баланс (HP, урон, вероятность граней) — отдельный документ/таблица.
- Ассеты (арт, музыка) — отдельная задача; на старте — плейсхолдеры.
- Переводы/локализация — требуется ли и сколько языков, уточнить на этапе UI.
- Web-версия — не таргет.

## 9. Риски

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Сортировка глубины в изометрии ломается на высоких объектах | средне | визуальные артефакты | Правило «нога спрайта» + ранний тест на сложной карте |
| Свой A* окажется медленным/неточным на сложных картах | средне | застревающий ИИ | Тесты на картах с препятствиями; ограничение области поиска |
| Производительность на слабых мобайлах (много спрайтов) | средне | фризы | `SpriteBatch`, кэш `TextPaint`, куллинг внеэкранных тайлов |
| Боёвка получится UI-перегруженной, драг-н-дроп неудобен на тач-экранах | высоко | портит ядро игры | Прототип боёвки — самый первый играбельный вертикальный срез |
| Разрастание контента без редактора | средне | медленный контент-пайплайн | JSON-схема + валидация на старте; позже — простой редактор |

## 10. Этапы разработки (очерёдность)

1. **Боевой прототип.** Логика боя + минимальный UI: бросок кубиков, перетаскивание
   в слоты, один враг, конец боя. Это ядро игры и главный риск — делается первой.
2. **Изометрический мир.** Тайлы, камера, движение, коллизии, переходы между
   картами.
3. **Связка.** Столкновение на карте → запуск боя → награда → возврат в мир.
4. **RPG-обвязка.** Инвентарь, экипировка, прокачка, классы.
5. **Сюжетный слой.** Диалоги, флаги, события (когда будет текст).
6. **Контент и полировка.** Контент из JSON, звук, настройки, сейвы, баланс.
7. **Релизная подготовка.** Иконки, сборки под Android/iOS/десктоп, тесты.

## 11. Открытые вопросы (уточняются по мере разработки)

- Управление на мобайлах: только тап-ту-мув или ещё виртуальный стик?
- Локализация: один язык или несколько на старте?
- Соотношение глубины RPG и длины забега (короткие рогалик-раны vs длинная
  кампания)? От этого зависит устройство сейвов и мета-прогрессии.
- Нужен ли редактор карт сложнее Tiled (для внутриигровых подземелий)?
